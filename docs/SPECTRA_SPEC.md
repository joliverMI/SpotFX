# SPECTRA spec — the live reconciliation surface

This is the thing that did not exist before 2026-08-15, and its absence is why the Admiral kept
finding capability gaps himself minutes after someone reported nothing was missed: there was
nothing to reconcile against. This file is that reference. It is not a design doc, not a
tutorial, not a status report — it is a **ledger**: every SPECTRA-relevant capability, its
honest current state, and every open decision that blocks something.

**Read [Maintenance protocol](#maintenance-protocol) before editing this file.** Everyone who
touches SPECTRA touches this file when one of three trigger conditions fires — that is what
keeps it live instead of becoming the next stale artefact nobody trusts.

Origin: Admiral-authorised 2026-08-15 (`data/backlog.md` `spectra-live-spec`), built from
`data/spotfx-capability-audit/report.md` (46 capabilities, code-cited, dated 2026-08-14),

## Maintenance protocol

**Who:** any agent working on SPECTRA — crew, Captain DJ, firstmate. Nobody owns this file
exclusively; whoever hits a trigger condition below edits it in the same change.

**When — exactly three trigger conditions, no others:**
1. **A PR proving a capability lands** (merges to `master`) → flip that row's state, cite the
   PR number, delete any now-stale "unverified" note.
2. **The Admiral answers an open question or states a new decision** → see *Translating an
   Admiral edit* below. This is the one that needs care.
3. **An audit or code check finds this ledger wrong** — a row claims a state the code no longer
   matches → fix the row, tag it `(code-verified <date>)`.

Do not edit this file to tidy prose, re-narrate the audit, or record day-to-day PR review/CI
status — that churn belongs in `data/backlog.md` (fleet-managed, changes hourly). This file
tracks **capability state and decisions**, which change far less often than task-queue status.

### Translating an Admiral edit (read this before touching his text)

When the Admiral edits this file directly — a sentence dropped into a row, a correction, a
comment — **his words are a statement of intent, not a patch to merge as-is.**

1. **Do not leave his sentence sitting next to the structured parts unconverted.** It will rot:
   nobody will translate it later, and the next agent will either misread it as binding prose at
   the wrong altitude, or ignore it and lose the intent entirely.
2. **Find or create the correct structured slot for it** — a ledger row's State/Notes, a new row
   in [Open questions](#open-questions), a new or amended line under
   [Standing decisions](#standing-decisions) — and write the intent into that slot, in the
   document's own vocabulary (the state legend, the table columns). Translate, don't transcribe.
3. **Record that his edit drove it.** Append `(Admiral edit, <date>: "<short paraphrase or
   verbatim clause>")` inline at the point of change. This is provenance, not decoration — it is
   what lets a later agent tell "he decided this" apart from "we inferred this from code."
4. **If his sentence doesn't cleanly resolve into an existing slot** — it's ambiguous, or answers
   a question nobody had asked — don't force-fit it. File it as a new row in
   [Open questions](#open-questions) naming what's ambiguous, with a note that it came from a raw
   edit, and ask him directly rather than guessing.
5. **Never delete his raw sentence before doing 1–4.** If you genuinely can't resolve it in the
   same sitting, move it verbatim into
   [Unprocessed Admiral notes](#unprocessed-admiral-notes) at the bottom rather than losing it or
   leaving it stranded mid-document. That section should be empty in steady state — its presence
   at all is a signal something is owed.

## Standing decisions

### D1 — The fidelity rule

> "Exact where there is a direct equivalent, free where the mechanism differs in kind."
> (Admiral, 2026-08-14, `data/captain.md`)

Where SPECTRA has a like-for-like control — a button, a mode, a thing doing the same job as the
old SpotFX one — **any difference he can feel is a defect, not a design choice.** Read the old
implementation's real numbers before writing. Where the mechanism is genuinely different in kind
(continuous colour drift replacing on/off triggers), build for the same intent and let him
correct it after living with it.

This is why the ledger's `BUILT` state carries a fidelity qualifier (`full` / `extended` /
`partial`): `full` claims exact fidelity to a direct legacy equivalent; `extended` claims the
free half of the rule (same intent, different — and here, richer — mechanism); `partial` is not
a fidelity claim at all, it's an honest "narrower, and nobody is currently building the rest."

Worked failure case on file: the ambient release shipped 2026-08-14 copied legacy's fade numbers
exactly but omitted its second phase, an ~8s eased catch-up — he caught it by watching. Fixed in
PR #61; see §6.

### D2 — The day-one switchover bar is four items, not three

> "Add colour-set authoring and the trigger migration to the bar."
> (Admiral, 2026-08-14, widening his own earlier 3-item bar)

Blockers to switchover: **dark/light mode (§9), colour-set and group authoring
(§10), the trigger migration (§44)**. Force Scene (§31) and Ambient
(§6) are DONE. Current state of all four: [Day-one bar](#day-one-bar) below.

### D3 — Step-through triggers: closed, not building the mini-timeline

> "The flare-and-return moment is what I valued." (Admiral, 2026-08-14)

The ordering/choreography of legacy's multi-step triggers was incidental; what he valued is the
moment everything flares and snaps back. Extend the cheap flare-and-snap-back mechanism (named
flare kinds, momentary hold — §11) instead of building the Sequence/Parallel
mini-timeline-inside-a-scene. **Closed as answered — do not raise it again unless he does.**

### D4 — Legacy retirement is gated, not scheduled

The legacy SpotFX authoring world (events/triggers/choosers) retires **only** on the Admiral's
satisfaction with SPECTRA plus his explicit destructive word on the day
(`data/backlog.md` `spotfx-legacy-retirement-gate`, corr=821f1ec08f6cb466). Every `GAP` and
`OLD-WORLD` row below is safe today only because legacy is still the thing actually driving his
room — S3 hardware handover ([`docs/SPECTRA_HANDOVER.md`](SPECTRA_HANDOVER.md)) is built and
proven but gated off. Nothing in this ledger implies urgency beyond what the day-one bar (D2)
states.

## Confidence & scope of this document

- Ledger states are grounded in the 2026-08-14 capability audit (46 capabilities, code-cited,
  `data/spotfx-capability-audit/report.md`) plus a direct code/backlog re-check run while writing
  this spec (2026-08-15) to catch same-day drift. **Where the two disagreed, the code won** —
  those rows are tagged "DELTA since audit" (currently: §6).
- **What this document does not cover:** settings/config minutiae the audit itself deliberately
  grouped into parent capabilities rather than itemising (its own stated limitation, inherited
  here); anything outside the original 46 + the day-one bar + backlog captain-decision items as
  of 2026-08-15; exact on-screen animation feel or gesture nuance — the audit is source-only, no
  live UI runs, and this spec carries that same caveat forward rather than re-verifying it.
- **Confidence:** MEDIUM-HIGH on rows carried straight from the audit (inherited, not
  re-derived). HIGH on the rows independently re-checked against current code while writing this
  spec: §6, §7, §9, §10, §44 (grep-verified 2026-08-15, cited inline above).
- This spec deliberately does **not** track day-to-day PR review status, CI results, or
  room-window scheduling — see [Maintenance protocol](#maintenance-protocol). That's
  `data/backlog.md`.
- **A stale row here is worse than a missing one.** If a `BUILT` marking looks surprising, check
  the code before repeating it in front of the Admiral — do not trust this document blindly, the
  same failure that made it necessary in the first place.
